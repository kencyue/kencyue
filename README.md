## Hi, I design tools by placing solutions at the right boundary.

### How I Approach Problems

I don’t start by asking *what technology to use*.  
I start by asking *where the solution should live*.

- If a problem can be solved on the user side, it stays there.
- If no shared state is required, I avoid infrastructure.
- If a task can be delivered as a small, portable artifact, I prefer that over systems that need deployment and maintenance.

---

### My Engineering Style

I favor solutions that are:

- Close to the user
- Cheap to run
- Easy to move
- Easy to reason about when they fail

Complexity is introduced **only when the problem itself demands it**, not as a default.

---

### Scope of Work

Some problems belong near the user.  
Some belong closer to machines and physical systems.  
Some require coordination in between.

I’m comfortable working across these boundaries — and, more importantly, choosing *not* to use a layer when it adds no real value.

---

### Background

I’ve worked with both modern and legacy systems, software and hardware, simple tools and complex environments.  
That experience shapes how I evaluate trade-offs, performance, and long-term cost.

---

### What You’ll Find Here

- Small, focused tools
- Practical solutions built for real tasks
- Projects optimized for usefulness, not spectacle

---

### What I Don’t Optimize For

- Trends
- Impressive architectures
- Solving problems that don’t exist yet

---

If you believe good engineering is about **putting solutions where they belong**,  
you’ll probably understand this work.
